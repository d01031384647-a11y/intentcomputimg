# 李冀《酒店旅游行业小模型规划》评估

**日期**：2026-08-26 ｜ **评估依据**：方案全文（飞书文档 3 页，含五阶段/资源表/风险表）+ 此前判决（reports/2026-08_行业小模型蒸馏与开源论证，raw/34-35 共 48 次检索证据）
**结论先行**：**方案的前半部分（数据基建+评测体系）专业且应立即采纳；后半部分（蒸馏训练+开源）建立在一个与实测数据矛盾的前提上，维持"挂触发器、现在不做"的判决。这不是否定方案，是把方案切成"现在做的"和"条件满足再做的"两半。**

---

## 一、方案里的真金（两块，立即采纳，都不需要训练）

1. **LLM 代理层（记录大模型入参出参作语料）**——方案第一节的系统改造。**这正是公司未来最值钱的资产生产线**：Fin/Harvey 式"专有数据后训练"的入场券就是这些日志。评估：立即开工，工作量 1–2 天，与训不训模型无关，本来就该做。
2. **测试集构建方法论**——四类样本配比（真实 60%/合成 20%/边界 15%/对抗 5%）、三层版本化（固定基线集/动态更新集/压力验收集）、修一个线上问题就进回归集。**这是全方案最专业的部分**，直接拿来做两件已排期的事：①质量仪表（每条建议的事后验证）②HotelBench 行业评测集。唯一修正：**评测的对象从"自训模型"换成"提示词与工作流版本"**——我们每周迭代的是 prompt/规则/系数，同样需要回归测试防止改好一处坏三处。
3. 附带采纳：行话集/术语库（提升现有 prompt 专业性，零训练成本）。

## 二、致命的前提错误（方案第一句话就与实测矛盾）

方案开篇："长期依赖外部大模型 API 存在**成本较高**、响应延迟及数据隐私等潜在风险"。逐一检验：

| 理由 | 检验 | 判定 |
|------|------|------|
| **成本较高** | 实测：每店每月 API 成本 20–60 元；45 店满配约 1–3 万/年。方案自己的资源表：**首月 GPU 就要 4–5 万且注明"一个月肯定不够"**——首月训练费 > 全年 API 费，还没算占 50% 工时的数据工程人力（李冀月薪口径 5 万）。全口径参照 raw/35：年化维护 15–40 万，打平需 300–1600 家店 | ❌ 不成立，且被方案自己的数字反驳 |
| 响应延迟 | 调价是分钟级任务不是毫秒级；bot 对话的延迟瓶颈在网络与排队，7B 本地快的前提是有 4090——**酒店前台电脑没有**。方案没有回答"小模型部署在哪"：云端自托管则 GPU 服务器持续成本高于 API；端侧则 7–14B 在无显卡 PC 上跑不动（raw/35：3–4B Q4 才 10–15 tok/s） | ❌ 部署位置是方案最大技术空洞 |
| 数据隐私 | 有一分道理（经营数据出店），但方案同时计划**把脱敏数据集开源**——用隐私论证自建，再亲手把数据公开，自相矛盾。其风险表也自评"数据合规与隐私：中" | ⚠️ 论证自相矛盾 |
| 自主可控 | 真实的期权价值（API 涨价对冲，DeepSeek 8/17 起部分档涨价 11 倍）——但期权≠现在行权，已写入触发器 | ⚠️ 归入触发器 |

## 三、其他技术问题（按严重度）

1. **时序倒置**：方案要求 ≥10 万条高质量问答、测试集 60% 来自"线上日志与客服记录"——**系统 8/31 才上线，语料生产线还没转，就要开始消费语料**。真实数据不足时只能靠 DeepSeek/千问合成为主——蒸馏出来的是"DeepSeek 的通用能力复印件"，任何人都能复现，开源了也无独特价值。正确顺序：先跑 6–12 个月代理层日志，攒下别人没有的"建议→采纳→结果"语料，再谈训练。
2. **公开语料价值错位**：UNWTO/OECD/世行/OpenSky 是宏观旅游统计，对调价/评价回复/工单任务几乎无用——这是"为了有语料而找语料"。砍掉整个第 2 节的爬取计划（还附带爬虫合规风险）。
3. **基座选型前后不一致**：开篇 Qwen2.5-14B 或 Llama-3.1-8B，正文又建议 Qwen2.5-7B——说明选型尚未认真收敛；且 Llama 系对中文任务非最优，2026 年再提 Qwen2.5（而非 Qwen3 系）也偏旧。
4. **开源部分维持原判决**：零个已核实的"开源垂直模型换商业回报"案例（raw/34）；开源用自有日志衍生的数据集=把唯一独特资产送给同行；成功自研者（Fin/Harvey/Cursor）全部规模化后+全部闭源。
5. **机会成本此刻最尖锐**：今天 8/26，1.0 本周交付（8/31），方案自评"数据准备占 50% 工时+评估 25%"——这是一个全职项目，直接抽干 M0–M1 的算法火力。

## 四、给"成本-体验平衡"的正确解法（回应方案的合理关切，本周可上线）

方案的分层思想（高频简单任务用小的、复杂任务用大的兜底）**方向是对的，但实现错了**——不需要自训模型，用 **API 分层**即可：
- 高频轻任务（评价回复、格式化、分类、卡片文案）→ 轻量档 API（千问 Flash/豆包轻量档，输入 0.075–0.2 元/M，约为旗舰价的 1/10–1/40）
- 复杂推理（调价建议、归因分析）→ 旗舰模型，一分不省
- 效果：整体推理成本再降 50–70%，工作量 1–2 天路由改造，**达成方案想要的"成本与体验最佳平衡"，成本是训模型路线的 1/100**。这件事可以立即让李冀做，也算回应了他的成本关切。

## 五、批复建议（供你与李冀沟通）

> 方案批复：**第一、四、五节的前半部分（LLM 代理层、测试集体系、A/B 与灰度能力）批准立项，命名为"数据与评测基建"，李冀任 owner，9 月与 1.1 并行推进；训练与开源部分挂公司已定的三条触发器（活跃店 ≥300 / API 年支出 ≥50 万 / A 轮后专职团队），每季度由你出《基座与成本水位评审》时一并复核；公开宏观语料爬取取消；作为替代，请你本周先落地 API 分层路由（预期再降推理成本 50–70%）和行话集。**

这样处理的好处：方案 60% 的内容被采纳且立即开工（保护积极性与专业判断的尊严），被拒的 40% 有明确的重启条件（不是人否定人，是数字没到），且他关心的"成本"得到了一个本周见效的正解。

## 六、一句话总结

**这份方案证明李冀有训模型的完整肌肉——但它开篇的成本前提被我们自己的账单反驳（首月 GPU 费＞全年 API 费），它需要的语料要等生产线先转起来。把方案切两半：数据与评测基建现在就干（那是入场券），训练与开源等触发器（那是行权）——顺序对了，这份方案迟早有用武之地。**
